# 订货模板交互优化：落地文档

制定日期：2026-10-10。后续已按价格口径确认扩展至模板接口与定价服务。

> 历史方案说明：本文记录当次优化方案。后续已改为每个供应商独立维护门店销售价，结算周期也从商品展开区迁至独立“结算配置”。当前规则见 `docs/template-current-spec.md`。

## 一、业务背景（改动前需对齐的口径）

订货模板是门店的订货契约，同时约束四件事：

| 契约面 | 数据载体 | 下单时如何生效 |
| --- | --- | --- |
| 能订什么 | `TemplateItem` | 门店目录只渲染模板内商品，提交时二次校验 |
| 谁来供 | `TemplateItemSupplier` + `priority` | 提交时校验供应商是否在关联内，priority 决定首选 |
| 多少钱 | `TemplateItem.initialSalesPrice` + 模板价格版本 | 每个模板商品只有一个门店销售价；供应商供货价独立读取公共成本 |
| 怎么结 | `TemplateStoreSupplierCycle` | 门店 × 供应商 覆盖账期，未覆盖则回落供应商默认账期 |

两条不可动摇的口径，改动必须保持：

1. **模板只管售价不管进价**。商品参考销售价只负责初始化，模板商品销售价是门店下单唯一售价；进价恒取供应商公共供货价，模板不得影响供应商结算基准。
2. **账期只对账期类供应商有意义**。`resolveSettlementTerms` 对非 `SUPPLIER_TERM`/`COMPANY_TERM` 的供应商强制 `IMMEDIATE`，界面上必须让管理员看出一致，不可提供看似可配实则无效的控件。
3. **模板不重复维护供应商范围**。模板商品自动继承商品管理中的全部有效关联供应商，只在模板内配置首选供应商；供应商增删回商品管理维护。

`TemplateStoreSupplierCycle` 是 `template + store + supplier` 三元组，本质是**同一模板下不同门店对同一供应商给不同账期**，这是真实业务中最常见的诉求，也是本次交互要支撑的核心场景。

## 二、现状缺陷

### D1账期草稿不回显（功能性缺陷）

`TemplateProducts.tsx` 的 `cycleFor()` 仅读取 `detail.cycleOverrides`，即服务端已保存的值。管理员在下拉中选择新周期后，`onCycleChange` 将值写入父组件的 `cycleDraft`，但组件自身无任何处读取该草稿。

后果：下拉仍显示旧值（通常为"默认"），管理员改完看不到自己改了什么；对相同值再次选择不会触发 `onChange`，草稿可能残留旧值。

### D2 门店多时账期矩阵宽度失控

账期网格使用 `minmax(150px, 1fr)` × 门店数。3 门店约 650px 可接受；8 门店约 1400px，将与 Modal 宽度 1400px 冲突。每个商品展开都需重新横向滚动，且各行滚动位置独立，管理员容易迷失。

### D3 账期存在双入口且规则不一致

| 入口 | 覆盖范围 | 问题 |
| --- | --- | --- |
| 商品展开行内 | 该商品关联的供应商 | 新入口 |
| 独立"结算周期"弹窗 | 全部 enabled 商品的供应商 | 旧入口 |

独立弹窗存在两个具体缺陷：
- `Form.List` 内直接调用 `form.getFieldValue` 读取字段，绕过 `Form.useWatch`，切换门店时表格不重渲染。
- 结算方式列为二元判断 `mode === 'SUPPLIER_TERM' ? '供应商账期' : '公司账期'`，会把储值、挂账供应商错误显示为"公司账期"。

双入口必然产生口径分歧，且旧入口的展示存在错误信息。

### D4 主表列信息冗余且可能误导

主表 9 列，其中 `默认销售价`/`供货价格`/`预估毛利` 三列只取**首选供应商**的值，但列标题为中性词（"供货价格"），用户看到的是单一数值，无法得知它只代表首家供应商。

### D5 展开行内供应商信息重复三次

展开后供应商名分别出现在：主表供应商列、展开行供应商表、账期矩阵左侧标签列。同一屏三处重复。

### D6 反馈缺失

- 修改价格或账期后界面无任何未保存提示，仅底部一行静态汇总。
- 毛利为负（如 -20%）与正毛利视觉无差异。
- 非账期供应商的"即时结算"占位文字占满单元格，形成大片视觉噪音。
- Modal 宽度 `width={1400}` 为固定像素，小屏溢出视口，与项目其他页面的 390px 适配惯例不一致。

## 三、优化方案与验收口径

### O1 账期草稿回显（对应 D1）

父组件将 `cycleDraft` 传入 `TemplateProducts`，`cycleFor()` 优先读草稿，其次读已保存值，最后回落空值（显示"默认"）。

验收：选择周期后下拉立即显示所选值；切换到其他商品再返回，值保持；关闭弹窗放弃修改后回到已保存值。

### O2 账期布局按门店数降级（对应 D2）

- 门店数 ≤ 4：保持横向网格。
- 门店数 > 4：改为**按门店纵向分组**，每组一个折叠面板，面板内列出该门店涉及的全部供应商周期，避免横向溢出。

验收：5 个以上门店时不再出现横向滚动；任一门店的周期均可通过滚动到达。

### O3 移除独立"结算周期"弹窗（对应 D3）

商品展开行内的账期矩阵已能覆盖全部场景，下掉独立弹窗入口（`Mode` 中的 `cycles`、`cycleStore`、`initialCycles`、`cycles` 表单字段及对应操作按钮一并移除），只留单一入口。

验收：操作列不再出现"结算周期"图标；模板内全部账期均可在商品编辑器中配置完成。

### O4 主表价格列合并（对应 D4）

主表明确展示「参考销售价」与可编辑的「门店销售价」。供应商供货价和按该门店销售价计算的预估毛利放在展开行中；多供应商共享同一个门店销售价。

验收：多供应商商品的价格列能看出取自首选；负毛利有视觉区分。

### O5 合并展开行内两张表（对应 D5）

将展开行内的"供应商表"与"账期矩阵"合并为一张：每个供应商一行，左侧只展示该供应商供货价与按模板销售价计算的毛利，右侧为各门店周期。结算方式降级为行内文字标签，不再单独成列。

验收：展开单个商品只呈现一张表，供应商名只出现一次；"即时结算"以 `—` 加 tooltip 呈现。

### O6 反馈与适配完善（对应 D6）

- 底部汇总条在存在未保存修改时显示「● 有未保存修改」。
- 弹窗宽度改为 `min(1400px, 94vw)`，兼容小屏。

验收：任意编辑后底部出现未保存提示；390px 视口下弹窗不溢出视口。

## 四、实施顺序

1. O1（草稿回显）—— 纯缺陷修复，独立可验证
2. O3（移除旧入口）—— 消除双入口，为O2/O5 让位
3. O5（合并两张表）—— 在无旧入口干扰下重构展开行
4. O2（布局降级）—— 依赖 O5 的最终结构
5. O4（主表列合并）
6. O6（反馈与适配）

## 五、不做的事

- 不新增数据库字段；沿用模板项现有价格字段承载当前模板销售价，并同步模板价格版本。
- 不改商品管理的供应商关联口径（模板仍只读展示，增减供应商回商品管理维护）。
- 不引入"移除供应商"能力。
- 不做浏览器自动化验证（按用户要求由用户自行验证），本轮以 `npm run check:admin`、`npm run build:admin`、`npm test` 为准。

## 六、风险

- O3 移除旧入口后，若独立弹窗曾有用户依赖的独有配置能力，需确认无遗漏。经核查其能力完全被展开行矩阵覆盖，且其结算方式列存在错误展示，移除为净收益。
- O5 合并两张表会改变展开行的 DOM 结构，需同步调整 `TemplateProducts.css` 中 `.template-supplier-expanded`、`.template-cycle-grid` 等类，改造后须检查 390px 视口表现。
