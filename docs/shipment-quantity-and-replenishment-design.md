# 发货数量修订与补发设计

## 1. 目标与现状

本设计补齐供应商少发、发货数量更正、门店少收、补发授权及按实收结单的完整履约闭环。当前系统已有发货批次、收货修订、差异、补发缺口等模型，但发货明细创建后不可修订；差异由供应商选择补发/同意/退回，既没有少发凭证与备注强制校验，也没有由门店决定是否补发的明确授权。因此仅调整页面无法满足需求，需同步改服务端权限、数据模型、资金核算和历史兼容。

业务要求以 [需求 §5.5-5.8](./requirements.md#55-供应商发货管理可拒单) 为准；总体领域约束见 [架构 §5.3](./architecture-design.md#53-减量与缺货补发)。

## 2. 数量定义与不变量

对每个供应商订单商品定义：

| 量 | 含义 | 规则 |
|---|---|---|
| `Q` 原下单量 | 采购确认后冻结的订货数量 | 不可被供应商或收货动作改写 |
| `Sᵢ` 批次发货量 | 第 i 个普通发货/补发批次的当前有效数量 | 普通发货更正不超过 Q；门店确认该批次后锁定 |
| `Rᵢ` 批次实收量 | 门店对第 i 个批次确认的当前有效实收 | `0 <= Rᵢ <= Sᵢ`；收货最终确认前可修订 |
| `G` 授权待补量 | 门店明确要求补发但尚未完成的数量 | 供应商补发不可超过尚未履行的 G |
| `F` 最终结算量 | 完成履约或按实收结单后参与结算的数量 | `F <= Q`；历史版本不得重复计入 |

补发是替代履约，不是订单增量：首批已发 10、门店实收 8 并授权补 2 时，供应商可以物理再发 2，累计物理发货为 12，但最终结算最多 10。若门店按实收结单 8，则 `F=8`、剩余 2 关闭，不得再补发。不得把所有发货批次简单相加当成可结算量。

核心校验：

- 当前批次修订量为非负数，且不超过该商品原下单量；多个普通发货批次累计不得超过 Q。少于原下单量的发货修订必须提供备注和凭证。
- 补发批次必须绑定一个仍开放的门店授权缺口，且分配量不超过其剩余授权量；禁止无缺口补发和重复消费授权量。
- 每批次实收不得超过该批次有效发货量。退款/释放、应收应付及利润按最终有效结算量和价格快照计算。
- 门店可对已提交但尚未最终确认的本批实收修订；一旦最终确认，不允许原位覆盖，只能通过受控的退回核对流程产生新版本。
- 同一商品最终结算量不超过 Q；供应商不能增加原单需求，采购改派属于另一条既有受控流程。

## 3. 角色与页面流程

### 3.1 供应商发货与更正

1. 供应商打开未最终收货的批次，查看原下单量、当前有效发货量、已收/待收、已授权待补量。
2. 可在门店最终确认本批收货前提交修订。页面明确展示原值、新值和差值；更正不会删除旧版本。
3. 若修订后有商品低于 Q，要求上传至少一份凭证并填写非空原因/备注；凭证和备注关联整个订单修订，同时每个少发商品记录数量。缺任一项不得提交。
4. 若门店正在填写收货，提交后使旧草稿失效，并提示门店按最新发货版本重新核对。
5. 门店已最终确认的批次只读。供应商如需补货，必须使用门店已授权的补发任务，不通过修改旧批次增加数量。

### 3.2 门店收货与处置

1. 每批次显示商品原下单量、当前批次有效发货量、累计有效实收、授权待补量、供应商少发凭证和备注。
2. 门店填写本次实收量，默认当前批次发货量，可改为实际数量；提交前可再次调整。
3. 当该商品尚未达到 Q，门店必须选择其一：
   - **要求补发**：授权量按 `Q - 已确认有效实收 - 仍在途且未作收货结论的有效量` 计算；不产生多余授权。对当前批次少收的场景，确认后形成待补任务。门店按钮、确认弹窗及供应商提示统一使用“要求补发”，技术层面的授权缺口规则保持不变。
   - **按实收结单**：按门店确认的有效实收结清该商品未完成部分，关闭尚未履行授权量，执行资金差额调整；后续不可再补发。
4. 若实收加在途有效量已足 Q，不产生短缺选择；仍有待收批次时订单不得提前完成。
5. 补发到货后门店再次按批次收货。若再次少收，可对尚未关闭的差额重复选择；历史授权/履约均可追溯，不能重复核销。
6. 供应商认为实收数量错误时，只能申请“退回门店核对”。门店重新检查并提交新收货版本；供应商不能选择“接受少收”替门店关闭缺口。

### 3.3 状态表达

订单履约状态由行项目和批次汇总，不新造混合资金状态：

`待发货 → 待收货 → 待门店选择 → 待补发 → 待补收 → 待完成`

供应商修订已发货数量后可展示“发货信息待门店确认”。退回核对时展示“门店重新核对”。订单仅在每个商品达到 Q，或被门店按实收结单，且无在途批次、待选决策、未履行授权缺口时完成。列表/详情必须能区分“供应商少发待决定”和“门店少收待决定”，不可都只显示“异常”。

## 4. 数据模型与迁移方向

现有 `Shipment` / `ShipmentItem`、`Receipt` / `ReceiptItem`、`Discrepancy`、`ReplenishmentGap` 可复用，但需要表达发货修订和门店授权决策。建议迁移采用追加表/字段，不重写历史：

- 新增 `ShipmentRevision`（或等价修订实体）：shipment、revision、提交人/角色、时间、订单版本、备注、当前标记；关联该版本的商品数量及差异凭证。当前生效版本唯一，旧版只读。
- 每个发货修订商品明细记录数量及是否普通发货/授权补发分配；不能只改 `ShipmentItem.quantity`。
- `ReplenishmentGap` 增加来源类型/决策人/决策时间/关闭原因和版本；门店授权是创建/增加缺口的唯一入口。原 `discrepancyId` 唯一约束可能不足以支持多次授权，需要评估改成一条差异对应多次授权事件，或将 gap 改为按商品的追加台账。
- `DiscrepancyActionType` 不再让供应商执行 `ACCEPT` 以关闭门店缺口。保留旧枚举值仅兼容历史数据，不对新请求开放；增加门店 `REQUEST_REPLENISH`、`SETTLE_AS_RECEIVED` 与供应商 `RETURN_FOR_RECHECK` 等可审计动作。
- 供应商少发凭证使用独立文件业务用途和授权检查，不复用门店收货凭证。若现有文件用途枚举没有对应值，新增用途并限制上传/读取主体为该供应商订单双方。
- 订单/批次使用 `version` 或修订号做乐观并发控制；若数据库并发更新失败返回冲突，客户端刷新重试，不能静默覆盖。

迁移策略：既有发货记录视为初始版本 1；既有收货版本保持原 `isCurrent`；既有补发缺口映射为历史授权，不追补新凭证/备注；旧供应商 `ACCEPT` 动作保留为历史事实，不回放、不重算资金。迁移脚本先在副本/本地数据库验算关联数和数量恒等式，再执行正式库；不清理历史数据。

## 5. API 与事务边界

新增或演进命令（具体路由遵循当前模块风格）：

| 命令 | 权限 | 服务端必须校验 |
|---|---|---|
| 修订未确认发货批次 | 对应供应商 | 订单归属、批次未最终收货、修订号、数量上限、少发凭证/备注、凭证访问权 |
| 提交/修订门店收货草稿 | 对应门店 | 批次归属、批次修订号、`Rᵢ <= Sᵢ`、实收版本；最终确认后只可走退回核对 |
| 门店选择补发 | 对应门店 | 有效 Q、已收和在途量、未关闭缺口；同事务建立授权台账及通知 |
| 门店按实收结单 | 对应门店 | 结算数量、关闭剩余缺口、冻结/余额/挂账/账单调整及幂等键 |
| 供应商提交补发 | 对应供应商 | 只允许分配到有效授权 gap，数量不超过剩余额度；复用原订单价格与账期 |
| 供应商申请退回核对 | 对应供应商 | 仅针对当前有效收货版本，写理由和动作，不直接改收货/资金 |

每个会改变数量、gap 或资金的命令都在单一事务内锁定/校验订单版本，追加业务事实，更新当前有效指针/汇总，写资金流水和 outbox 通知，并按已有幂等约定处理重试。事务失败不得只保存发货却漏建授权/资金调整。

## 6. 资金、价格和报表

- 所有批次沿用供应商订单的价格快照；补发不新增商品货款、不按补发当天重新取价；额外运费仍走既有采购确认规则。
- 在门店选择补发期间，对未完成数量继续保留对应资金占用；按实收结单后按最终结算量释放储值冻结/挂账占用或生成退款/调整流水。
- 门店储值订单只在履约结论完整后按最终结算金额扣款；不因某一批收货或某一商品先结单重复扣款。账期订单按最终有效金额更新未结账单；已结清账单按既有差额调整单规则处理。
- 供应商销售/供货金额、利润、门店和公司结算报表都以最终有效数量为准。未完成差异标记为待核对，不提前作为已结算交易。
- 每个计算需明确区分已最终实收、未收在途、授权待补、按实收关闭量；绝不能把旧收货版本与新版本相加，也不能把补发物理量重复计入应收应付。

## 7. 分阶段实施

1. **服务端与数据**：先确定修订实体、缺口台账及文件用途，完成 additive migration、DTO、事务校验与历史映射。
2. **供应商端**：发货数量修订、差异凭证/备注校验、修订历史、授权缺口补发、冲突/已收货锁定提示。
3. **门店端**：批次收货编辑、少发/少收差异展示、逐商品补发/按实收结单决策、重复补发闭环及凭证预览。
4. **账务和查询**：按最终结算数量重算储值、挂账、供应商应付及报表，补充历史查询和审计。
5. **部署验收**：本地迁移与真实数据库集成回归通过后，再备份服务器数据库、部署 API/小程序并做线上只读核对；本设计文档本身不表示已经实施或部署。

## 8. 验收矩阵

| 场景 | 预期 |
|---|---|
| Q=5，供应商首次申报 3 | 缺凭证/备注不能保存；完整提交后门店看到 3/5 和证据，可选补 2 或按实收结单 |
| Q=5，供应商先报 5，门店实收 3 | 门店可授权补 2；供应商最多补 2，最终结算不超过 5 |
| Q=5，首批物理发 5，门店实收 3，授权补 2 后补收 2 | 累计物理发货 7 合法；最终实收/结算 5，货款不重复计入 |
| Q=5，门店实收 3 并按实收结单 | 资金按 3 结算，剩余 2 关闭，供应商无法再补发 |
| 门店收货草稿基于发货修订 r1，供应商提交 r2 | r1 草稿失效并提示刷新；不允许按旧发货量最终确认 |
| 已确认收货批次再次修订 | 拒绝；供应商只能使用门店授权补发任务 |
| 两端同时对同一批次/缺口提交 | 版本冲突或幂等返回；不可超授权、重复结算或重复扣退款 |
| 多商品部分补发、部分结单，订单重复提交 | 各商品独立决策；已消费 gap 不可再用，订单金额与流水只发生一次 |
| 老数据含供应商 ACCEPT / 既有 gap | 可查询历史；迁移不改变原数量、资金流水或订单状态 |

## 9. 当前实现状态与剩余工作

截至 2026-10-11，已完成首阶段可运行闭环：

- 新增发货修订版本及修订明细、凭证关联；供应商可在门店收货最终确认前修订当前批次，版本冲突会拒绝覆盖。
- 修订量不能为负或大于原下单量；少于原下单量时服务端强制要求说明和至少一张图片凭证。门店当前收货版本失效，并收到重新核对提醒。
- 门店提交收货后，系统按该发货批次的有效发货量与本批实收量生成差异；不能把尚未发出的订单余量混成本批少收。门店可选择授权补发或按实收结单。供应商不能替门店作该决定，只能将疑似收货错误退回门店复核。
- 供应商订单详情提供发货批次版本与修订入口；门店待办展示短缺处理入口。角色、对象归属和文件用途在 API 端校验。
- 初始发货、补发沿用订单价格快照；已有资金调整流程用于按实收结单。

已通过 `npm run build`、`npm test`（227 项）、`npm run mini:check`、`npm run mini:test`（148 项），以及本地 PostgreSQL 全量集成回归（745 项，0 失败）。权限矩阵也已覆盖新增发货修订、门店差异处置与对应文件上传权限。回归中发现并修正了差异被错误放大为订单未发货余量的问题；差异现以对应发货批次实发与实收之差为准。测试夹具清理已纳入发货修订历史，避免外键残留。

剩余验收边界：全量自动化回归通过，但尚未做真实微信客户端的人工端到端验收，也未在生产服务器部署本轮代码。当前已有集成测试验证一次授权补发、补发后再次少收及再次形成差异；并发补发超授权的专门竞争集成测试、长链路跨多轮部分补发与资金/报表逐笔对账仍建议作为专项验收，不应由一般回归通过推断已全部覆盖。正式部署前仍需备份、迁移演练及线上只读核对；本文档不表示已部署服务器。
