# 小程序产品设计与开发计划

## 2026-10-16 门店修改下货单

门店提交后、采购首次确认前，厨政经理可以修改原下货单：增减商品数量、添加或移除有效模板商品，至少保留一种商品。使用原下货单编号，保存后重新计算销售金额及储值/挂账占用，资金不足仍可保存。采购确认后锁定；财务退回仅由采购调整，不重新开放门店编辑。门店不可自行改价或指定供应商。小程序入口为下货单详情“修改下货单”。本节替代旧文档中门店提交后不可修改的说明。

## 2026-10-16 采购确认资金拦截（最终口径）

门店资金不足仍可提交和修改下货单；采购确认时实时核验储值和挂账额度，任一不足不得确认或生成任何订单。确认页分别显示所需、本单可用（包含本单已有占用）、待充值金额和待补挂账额度。采购可保存调整，财务负责充值/调额，补足后采购重新核验并确认生成供应商订单，不再经过独立财务审核。储值实际扣款仍在收货时进行。

`GET /purchase-requests/:id/confirmation-preview` 提供资金统计，仅采购经理/采购跟单授权范围及管理员可读；`confirm` / `confirm-adjusted` 成功直接返回 CONFIRMED 和生成订单 ID。服务端加锁事务校验，防重复生成及重复占用。历史 PENDING_FINANCE 单据由采购待办接续处理，不迁移或重建历史订单；原 finance-approve 不再允许生成订单。详见 [确认资金规则](./purchase-request-finance-review.md)。

## 2026-10-15 资金不足仍可提交下货单

储值或挂账不足均保留“提交下货单”按钮，分别展示缺口，提交成功显示资金待补足。生成供应商订单前必须校验全部资金组；不足时不生成任何订单。财务充值或调整挂账额度后，仍需重新执行确认，不能自动推送供应商。

## 2026-10-14 订单中心口径

本节及 [当前流程方案](./store-request-supplier-order-plan.md#当前确认口径2026-10-14) 覆盖旧版以门店订货单作为唯一主记录的设计。

- 采购确认前以“下货单”承载门店需求；采购最终确认后，门店和采购订单中心以正式供应商订单为主，保留下货记录入口用于待确认处理和来源追溯。
- 每张订单属于一个门店、一个供应商、一张下货单。一个供应商可以服务多个门店，订单不跨门店或跨下货单合并。
- 订单列表突出门店 / 供应商、完整订单号、商品、金额及状态；来源下货单号在门店及采购详情次要区显示。供应商围绕门店及自己的订单发货，不展示整张下货单或其他供应商内容。
- 不新增底部导航，不修改交易或资金规则。门店及采购订单主视图已接入共用 `order-center` 组件，独立保留下货记录；支持状态、单号、门店 / 供应商及创建日期筛选、订单详情及来源往返。微信开发者工具已检查门店和采购已有订单，不等同于所有状态的真机及写入全流程验收。API 仍全量读取，客户端按订单分段展示。

## 2026-10-11 当前流程与价格口径

本节保留当时确认的流程和价格口径；订单中心展示以 2026-10-14 章节为准，其余不冲突的规则继续有效。

- 门店提交下货单，采购最终确认才按供应商生成正式订单。提交阶段和采购确认前门店端不展示供应商信息；正式订单详情显示供应商分组及联系信息。
- 门店只能订购绑定的有效模板内商品；一个门店一个有效模板，一个模板可绑定多个门店。无模板时清空失效目录/清单并提示联系采购，历史订单及结果不确定的提交记录保留。
- 采购确认清单按供应商分组，商品行不重复供应商名称；有候选供应商时显示“更换供应商”。候选项限于该下货单模板为该商品配置的当前可供货供应商，预览金额影响后保存。
- 采购待确认详情只保留“确认并生成订单”主操作；进入页面及提交后自动更新，失败提供重试，不再常驻“刷新明细”按钮。成功后显示生成订单数、供应商、订单号及状态。
- 商品价格仅作资料参考；供应商价格为采购成本；销售价格来自模板中该商品与实际供应商的配置，新增默认取供应商价格，之后可独立调整。
- 采购商品行默认突出商品名称、订货数量及单位，销售金额为次要信息；清单顶部“价格明细”开关默认关闭，开启后显示双列销售价格、供应商价格及对应金额，价格和金额都保留两位小数，不显示商品价格。商品名旁设置更换供应商入口；默认供应商分组只显示名称及商品种数，顶部仅保留紧凑订货金额。价格解析取消缺失模板价的公共价格兜底仍待实施。
- 最新实施与验证状态见 [下货单与供应商订单流程](./store-request-supplier-order-plan.md)，价格规则以 [订货模板当前规则](./template-current-spec.md) 为准。历史测试数字和截图不代表这些待实施项已完成。

## 2026-10-09 操作布局优化

- 发货、拒单、采购确认、改派、运费审核及收款审核使用导航上方的固定操作栏，页面底部预留滚动空间。
- 采购确认按钮仅出现在待采购确认的订单；历史订单保留明细刷新，不展示无效的确认入口。
- 公司财务核对金额与驳回原因保留在正文，确认和取消统一在底部；只有一个最终提交按钮，提交中禁用。
- 读取失败时保留错误提示及数据刷新入口，不同时将失败状态描述为暂无订单或付款记录。
- 结清、资金不足及公司财务角色使用中文标签；收货数量区域支持窄屏换行，账户数字和长名称不撑破容器。
- 小程序页面测试 105 项及结构检查通过；五角色原生模拟器只读导航增加订单详情截图，共 14 张。发货表单、收款审核有单元与结构检查，但尚未以本轮真实待处理单据验证所有表单和真机键盘。

## 目标与边界

面向五个业务角色，以同一订单贯穿订货、采购审核、供货、收货和结算。
不将后台维护模块直接搬入手机端，不新增结算规则，不放宽接口权限。
STORE 为门店厨政经理，STORE_FINANCE 为门店财务，PURCHASER 为公司采购，SUPPLIER 为供应商，HQ_FINANCE 为公司财务。

## 信息架构

| 角色 | 首页 | 底部导航 | 主要任务 |
| --- | --- | --- | --- |
| 厨政经理 | 可订商品 | 订货 / 订单 / 我的 | 模板商品下单、确认收货 |
| 门店财务 | 本店账户 | 账户 / 订单 / 我的 | 查看储值、挂账、流水和账单，不下单、不收货 |
| 公司采购 | 采购待办 | 待办 / 订单 / 我的 | 审核订货、拒单改派、确认运费 |
| 供应商 | 供货待办 | 待办 / 订单 / 对账 / 我的 | 发货、少收核对、补发、收款核对 |
| 公司财务 | 收款核对 | 待办 / 账款 / 我的 | 核对门店付款、登记公司对供应商付款、查询收付款记录及双方账单 |

多角色账号保留工作台切换；单角色不显示无关角色入口。管理员沿用采购入口，不创建第六套业务界面。

供应商“我的”只承载业务入口：“供应商资料”和“供货商品”分别进入独立页面。资料页只读联系人、配送、结算和开票信息；供货商品页复用商品卡片，以左侧两级分类和右侧商品列表浏览，仅允许维护自身供货商品的上下架状态，不展示或维护价格。

供应商“对账”分为职责不同的两个页签。“收款核对”是待办与历史操作队列：公司或门店登记付款并上传凭证后，由供应商确认是否真实到账；供应商不能在这里发起付款。“结算账单”是周期汇总与追溯页，用于查看应付、待确认、已收、来源订单和关联付款。两者不合并，避免把到账确认误解为结算申请。

公司财务“我的”只保留一个“门店账户管理”入口，顶部已展示当前账号时不再重复用户信息。门店销账采用“选择未销账订单 → 核对销账信息”两步流程；筛选、逐单金额、供应商、凭证和本次总额都在最终提交前明确展示。

公司财务在“账款 → 供应商账单”详情中登记公司对供应商付款：选择应付明细后先请求服务端预览，展示核定可付金额，再填写付款日期、上传 PAYMENT 凭证并登记。公司账期的门店应收未结清、明细已被付款预留或金额发生变化时，预览/提交必须阻断；登记成功后付款记录进入供应商的收款核对待办，由供应商确认到账。付款登记是线下资金操作的记录，不代表小程序发起银行转账。

## 页面与状态原则

- 列表用于判断，详情用于核对，操作表单用于提交。订单详情不默认展开全部表单。
- 每页一个主要操作；不可逆操作展示对象、金额和影响，二次确认。
- 履约状态与结算状态分开，不将已发货等同于已完成，也不将挂账等同于已付款。
- 待办数量来自真实接口。无法读取显示错误与重试，不将失败解释成零待办。
- 只使用业务单号，不把内部 UUID 当作面向用户的标题。
- 少收与补发是订单异常，不是一级导航。待办可直接进入异常详情及原订单发货。
- 公司财务仅核对 STORE_TO_COMPANY 的待确认收款；COMPANY_TO_SUPPLIER 的收款由供应商确认。
- 写入保留版本校验、幂等键和结果待确认恢复；切换账号或关闭页面不能回填旧请求数据。

## 视觉规范

统一浅色背景与白色分区，分区不做浮动卡片；绿色主操作，琥珀色待处理，红色错误。
页面标题 32rpx，区域标题 28rpx，次要信息 24rpx；不随屏幕宽度放大字体。
门店/商品名称优先，单号/时间其次；金额右对齐，数量必须带单位。
底部导航三至四项；主要操作与安全区留出稳定空间；空态、加载、错误分别表达。
商品使用真实图片和空图占位，凭证查看保持鉴权，不使用公开 OSS 链接。

## 开发分期与验收

### 第一阶段：角色架构与真实入口（本轮）

实现五角色登录路由、门店财务默认账户、采购和供应商任务首页、统一导航。
公司财务新增收付款详情、凭证查看、门店收款确认/驳回、账单查询，并支持从供应商账单登记公司付款。
门店增加本店账单与明细查询，保留厨政经理订单中的收货入口。
验收：五角色默认页正确，无越权按钮，真实 API 读取成功；待办可到具体对象，版本和幂等机制保持。

### 第二阶段：完整订单体验

将订单详情、发货/收货操作、异常处理形成独立详情层级；提交后回到更新后的对象。
补充联系电话操作、履约时间线、按状态搜索与分段展示。当前接口仍读取完整列表，服务端分页不在本轮完成范围内。
统一错误和凭证缩略图处理，新增移动端明细展示规范。

### 第三阶段：资金操作与原生视觉验收

核对移动端充值、销账、公司付款的业务授权、凭证和收款账户要求，再决定上线范围。
在微信开发者工具和真机验收小屏/大屏、安全区、键盘遮挡、长名称、无数据、断网和重复点击。
未经原生截图与实机验证，不标注视觉验收完成。

## 业务验收顺序

厨政经理下单 → 采购待办审核 → 供应商待办发货 → 厨政经理从订单进入收货 → 门店财务核对账户流水。
账期订单另走门店付款提交 → 公司财务待办核对；公司付款由供应商核对。
异常单测试少收、安排补发、返回原订单补发、门店补收；已处理通知不可显示为新的待办。
