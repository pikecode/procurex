# 下货单与供应商订单流程

## 需求边界

- 门店提交的是下货单（PurchaseRequest），记录商品、数量及门店销售金额，不是供应商订单。
- 门店选品、提交确认和采购确认前的下货单详情不展示供应商、供应商联系信息或供应商分组。
- 系统内部保留模板首选供应商作为采购的初始分配，用于报价与资金校验，不代表已向供应商下单。
- 采购确认前可针对某个商品替换供应商，仅可选该门店模板中适用、当前可供货且有有效价格的供应商。
- 替换前展示销售金额、供应商金额变化；保存后按目标供应商对应的销售价格和供应商价格重新计算金额与资金。资金不足时不得生成订单。暂不新增门店二次审批流程。
- 替换供应商只修改下货单，不发送供应商订单。采购最终确认时，按最终供应商分组，一家供应商生成一张订单。
- 供应商只能看到分配给自己的正式订单；发货、收货、差异处理、结算继续针对供应商订单进行。
- 正式订单生成后不得使用确认前的换供应商接口修改；拒单等异常继续走现有改派流程。
- 确认、替换沿用版本校验、幂等提交、审计记录及角色权限。采购跟单不因此获得采购经理的供应商调整权限。

## 实施计划

1. 保留现有 create / reassign-preview / assign / confirm 接口及数据库结构，不另建重复订单模型。
2. 门店提交确认改为普通商品清单，采购确认前详情取消供应商分组；确认后保留供应商履约信息。
3. 小程序采购明细增加逐商品供应商选择，使用 edit-catalog 限制候选项，通过预览核对金额后保存。
4. 后台采购沿用已有调整供应商入口；核对文案与确认生成订单的边界。
5. 回归提交、替换、最终拆单、重复提交、确认后禁止修改及门店展示。

## 验收要点

- 提交下货单以及替换供应商都不生成供应商订单。
- 同一张下货单包含不同供应商商品，最终确认后生成对应的供应商订单。
- 某商品由 A 换为 B 后，最终订单只把该商品分配给 B。
- 门店在采购确认前看不到供应商信息，确认后可以查看实际履约供应商。
- 保存失败、预览失败、取消核对不修改商品分配；结果未知可恢复原提交。
- 本次不重置测试数据，不改历史订单，不部署服务器。

### 门店模板订货边界复核

- 一个门店只能绑定一个有效模板，一个模板可绑定多个门店。采购更换供应商必须限于该下货单所用模板的该商品供应商，且供应商启用、未归档、商品上架并有有效价格；保存事务内再次校验，不只限制页面候选列表。
- 门店商品目录及新下货单必须以当前绑定的有效订货模板为准，不允许回退到全量商品库；没有有效模板时禁止新下货。
- API 原有目录、报价和创建接口均执行该规则，创建事务内再次读取模板；此次没有改动服务端业务规则。
- 小程序收到无模板错误时，清空旧商品、已选清单及报价，隐藏订货底栏，提示联系采购配置有效模板。历史订单查看与收货不受影响。
- 已发送但结果不确定的下货命令保留原幂等键用于核对结果，不因为模板失效丢弃记录。
- 验证通过：144 项小程序测试、静态检查、TypeScript 构建和真实数据库 HTTP 测试（无模板目录/报价/提交均拒绝且无下货单，绑定后报价成功）。没有部署服务器。

### 价格口径及收尾状态（2026-10-11）

- 商品价格：商品资料参考价格；供应商价格：商品与供应商关联的供货价格；销售价格：模板中商品与实际供应商对应的门店交易价格。详细默认及计价规则见 [订货模板当前规则](./template-current-spec.md#3-三类价格)。
- 采购商品行现已显示下货单快照的销售价格、供应商价格、销售金额及供应商金额，单价带销售单位，全部保留两位小数；待确认分组与历史平铺详情使用同一口径，不显示商品参考价格。
- 顶部汇总统一两类金额，只在缺款状态显示待补资金；分组显示供应商名称及金额，商品行在名称旁保留更换入口，不重复供应商。订单列表补充订货金额，搜索空态和加载/错误分开。
- 待实施：其他模块旧价格文案按相同口径逐步统一，不将采购页改动视为全部界面完成。
- 待实施：移除缺少有效模板销售价格时的供应商公共价格兜底，补充缺价、未生效及更换供应商回归。本次只同步文档，不宣称这两项已完成。
- 本地分类测试数据核对：store1 / store2 分别绑定各自测试模板，每个模板有 54 件商品，其中 48 件为分类演示商品；admin 切换对应测试身份后按门店范围读取，不因管理员身份放开全商品库。该数量是当前本地测试数据快照，不是生产配置要求。

### 商品优先的采购确认布局

- 最新反馈覆盖上一轮价格全部展开的布局：默认展示商品名称、订货数量及单位，一项销售金额作为次要信息；供应商分组只显示名称与商品种数，保持更换供应商入口。
- 清单顶部统一“价格明细”开关，默认关闭，开启后显示原有两类单价、两类金额及供应商分组金额。返回列表或切换身份后恢复关闭，不影响取价、订单快照和业务提交。
- 更换供应商仍必须核对金额影响，详细价格可查看而不抢占日常商品审核的主视觉。
### 采购确认结果展示补充（2026-10-11）

- 确认成功提示“采购确认成功”和生成的供应商订单数量，下货单编号不作为处理结果标题。
- 生成订单区域按供应商展示正式订单编号、状态及商品名称、数量和单位，读取正式订单详情，不使用原下货单分组推算订单内容。
- 商品清单读取失败时显式显示错误，重新加载详情时重试，不影响已成功确认的订单。
- 正式订单商品默认展示销售价格、销售金额及数量单位；供应商价格、供应商金额通过区域内价格明细开关展开。价格使用正式订单快照，格式保留两位小数，不重新读取当前商品或模板价格。
- 采购及正式订单清单展示商品缩略图，点击预览，无图和下载失败显示占位。通过鉴权下载当前商品图片；图片不是历史快照，不影响订单交易数据。

### 门店订货单与供应商履约信息架构优化（2026-10-11）

#### 业务对象与门店用语

- 门店一次提交形成一张“订货单”（内部仍为 `PurchaseRequest`），代表门店的一次完整订货意图；门店不直接创建供应商订单。
- 采购确认前，订货单处于待采购确认/待补资金等状态，只展示门店商品、数量、销售金额和资金状态，不展示供应商及供应商分组。
- 采购确认后，系统按最终分配自动生成若干供应商订单。供应商订单是订货单下的履约分单，不是门店另行提交的订单。
- 门店订单列表以订货单为唯一主记录，不把供应商订单重复摊平成多条门店订单。订货单详情中再查看供应商分单及各自商品、发货、物流和收货进度。
- 对门店使用“订货单/订货单详情/提交订货单”等业务用语；API、数据库和采购内部可继续使用 `PurchaseRequest` / 下货单，不要求改数据模型或编号。

#### 页面交互规则

- 订单列表状态筛选使用“全部、待处理、履约中、已完成”；取消单在“全部”中以明确状态展示，不单独占用常用筛选位。
- 列表进度文案在采购确认前表达“等待采购确认”或“等待补足资金”；确认后表达“拆分为 N 家供应商履约”及已完成数量，不在拆单前泄露供应商信息。
- 详情确认前为单一商品清单；确认后将商品与对应供应商订单合并成可折叠的履约分组，每组只出现一次供应商名称，并在该组内展示商品、订单状态、配送联系和发货批次。
- 待收货通知放在订货单列表顶部，作为订单工作流的待办入口，跳转到现有收货处理视图；不新增底部主导航。
- 订货列表、订货详情、提交动作的门店文案统一使用“订货单”；供应商端仍以正式供应商订单为工作对象。

#### 本次实施范围与验收

- 仅调整门店小程序的信息层级、可见文案及待办入口，不改变 API、订单状态、财务计算、单据编号和供应商订单生成时机。
- 任一门店提交一次订货，无论最终拆成几家供应商，都只在门店列表显示一张订货单。
- 采购确认前不显示供应商名称、供应商联系人、供应商分组或供应商订单；确认后每家供应商只呈现一个履约分组，商品和发货记录归属清晰。
- 门店可从订货单详情看总金额和资金状态，并分别查看各分单的状态、物流/发货和收货处理入口。
- 有待收货批次时，订单列表顶部明确显示待处理数量并可直接进入收货；无待办时不占用页面空间。
- 保留现有订单记录与收货/财务流程，不迁移或重置数据，不部署服务器。
